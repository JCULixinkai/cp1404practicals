## Estimates

Regarding the **estimates** that you did for practical tasks...

### How was your estimate accuracy usually?

At the beginning, my estimates were only moderately accurate, and I often underestimated the time needed—especially for unfamiliar concepts, debugging, or refactoring. I was better at estimating “writing code” time, but I frequently forgot to include time for understanding requirements, research, testing, and fixes.

### How did your estimate accuracy improve or change during the course of the subject?

My accuracy improved over time because I started breaking tasks into smaller steps (understand/design/implement/test/commit) and adding a buffer for uncertain parts. With more practice, I became more familiar with common tasks (e.g., file I/O, function decomposition, Git workflow, unit testing), so my estimates became more consistent.

### What did you learn from doing these estimates?

I learned that estimation is not “guessing a number,” but a way to understand scope and risk—where I might get stuck, where research is needed, and where repeated testing happens. It also encouraged me to start earlier, reduce last-minute rushing, and reflect on which types of tasks I consistently underestimated.

## Code Reviews

### What have you learned from being reviewed by other people?

Being reviewed helped me realize that “it works” is not the same as “it’s maintainable.” Naming, structure, readability, edge cases, and consistent style matter a lot. I also learned to accept feedback openly and treat reviews as a tool to improve code quality rather than a personal criticism.

## Practicals

### Regarding the **practical tasks** overall, what would you change if you were in charge of the subject?

If I were in charge, I would: (1) provide a clearer post-prac checklist (common mistakes, must-do items, stretch goals), (2) offer more layered examples for harder topics (testing, class design, project structure), and (3) make feedback faster and more focused (e.g., top 2–3 improvements) so students can iterate quickly.

### What did you do really well for practicals in this subject?

What I did well was staying consistent—finishing and submitting pracs weekly instead of leaving everything to the last minute. I debugged systematically (reproduce → locate → fix → regression test) and gradually built better habits such as clearer naming, smaller functions, more readable code, and more frequent/smaller Git commits.
